# ДЗ №2: воспроизведение нагрузки

Готовый результат: [отчёт с четырьмя графиками и EXPLAIN](../reports/search/REPORT.md).

## Полный запуск

Понадобятся Python 3.14, Docker и Compose **2.24.4+** (используется `!override`). Из требований к машине: свободный порт 8081, несколько GiB диска и ресурсы на два контейнера по 2 CPU / 2 GiB. Генератор работает на хосте; при 1000 клиентах желательно иметь `ulimit -n` больше 2048. Весь прогон занимает несколько минут.

Из корня проекта:

```bash
# Если .env ещё нет, создать его и указать случайный JWT_SECRET длиной >= 32 байт.
cp .env.example .env
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-benchmark.txt
.venv/bin/python -m benchmarks.run
```

Если `.env` уже настроен — оставьте как есть. Дальше `run` всё делает сам: скачивает `people.v2.csv` в `data/`, собирает контейнеры и ждёт готовности API.

## Что делает сценарий

Запускается **отдельный Compose-проект `social-benchmark`**, и внутри него по очереди:

1. БД с собственной сетью и volume `social-benchmark_postgres_data`.
2. Только миграция `001` — без индекса поиска.
3. Приложение на http://localhost:8081 с обычным пулом из 10 соединений.
4. Загрузка ровно 1 000 000 анкет через `COPY`; реальные ФИО, даты и города — из CSV.
5. `VACUUM ANALYZE`, проверка количества, сбор статистики и планов без индекса.
6. Три повтора на 1/10/100/1000 клиентов: окно запуска 15 с, прогрев 3 с.
7. Миграция `002` с индексом и `ANALYZE`, сбор планов и те же замеры после индекса.
8. Проверка неизменности ответов, сохранение JSON, CSV, графиков PNG/SVG и отчёта.

Нагрузочные профили лежат в `queries.json`: там частые, более редкие и отсутствующие пары префиксов, все они равномерно чередуются по кругу. В прогоне нет ни регистрации, ни логина, ни фоновой генерации данных. Учётные записи загрузчика синтетические — для входа они не годятся; для обычного входа создайте пользователя через API.

После эксперимента БД остаётся с индексом и миллионом анкет. Исходный CSV в Git не включён, а результаты и все сжатые журналы отдельных запросов — включаются.

## Повторный запуск

Чтобы повторить замеры на уже загруженной выделенной БД:

```bash
.venv/bin/python -m benchmarks.run --reuse-data
```

Загрузчик проверит число записей и метаданные исходного файла. Без `--reuse-data` он принципиально не работает с непустой таблицей. Учтите: повторный прогон перезаписывает результаты в `reports/search/` — если хотите сравнить два разных эксперимента, сохраните предыдущие файлы. Обычный Compose-проект приложения при этом не меняется.

Параметры сценария можно двигать:

```bash
.venv/bin/python -m benchmarks.run --duration 30 --warmup 5 --repetitions 3 --reuse-data
```

Для отдельной пробной БД подойдёт `--rows 10000 --duration 3 --repetitions 1`. Единственное жёсткое правило: число строк нельзя менять при повторном использовании уже заполненной БД. И напомню, отчёт для сдачи построен на полном миллионе, а не на пробном массиве.

## Что именно измеряется

`benchmarks/load.py` создаёт заданное число асинхронных клиентов с keep-alive. Каждый отправляет запрос, дожидается полного ответа и только потом запускает следующий. В конце окна новые запросы прекращаются, все начатые дожидаются завершения; таймаут — 120 с.

- **Latency** — время от начала запроса до полного чтения тела, включая очередь и ошибки.
- **Throughput** — число ответов HTTP 200 с правильным телом, делённое на полное время с завершением очереди.
- Ошибки, статусы, реальная одновременность, CPU генератора и время завершения очереди сохранены отдельно; ошибки не увеличивают успешный throughput.
- В таблицах и графиках — медианы показателей трёх прогонов, разброс — min–max.
- Это closed-loop тест фиксированной одновременности. Он не доказывает способность выдерживать фиксированный внешний поток RPS без очереди — держите это в виду при интерпретации.

Перед нагрузкой выполняется проверка функциональной корректности. Во время нагрузки проверяются HTTP-статус и SHA-256 тела каждого ответа. SQL `EXPLAIN` использует тот же запрос и параметры, что HTTP-метод; планировщик к индексу не принуждается.

## Файлы и перестроение отчёта

```bash
.venv/bin/python -m benchmarks.report
```

Команда только читает сохранённые результаты и строит отчёт с графиками — ни API, ни БД ей не нужны.

- `reports/search/REPORT.md` — итоговый отчёт.
- `results.json`, `summary.csv` — данные каждого прогона.
- `seed.json` — количество, уникальность, частоты имён, контрольная сумма источника.
- `raw/*.csv.gz` — запись каждого HTTP-запроса.
- `explain/*.txt`, `explain/*.json` — планы и параметры БД обеих фаз.
- `latency-before/after.*`, `throughput-before/after.*` — четыре графика в PNG/SVG.

## Отдельные операции и остановка

```bash
docker compose -p social-benchmark -f compose.yaml -f compose.benchmark.yaml exec -T app \
  python -m benchmarks.seed --rows 1000000

docker compose -p social-benchmark -f compose.yaml -f compose.benchmark.yaml exec -T app \
  python -m benchmarks.database --stage after

docker compose -p social-benchmark -f compose.yaml -f compose.benchmark.yaml down
```

`down` массив сохраняет. Удалить **только тестовую БД** можно той же командой с `down -v` — обычная БД приложения живёт в другом Compose-проекте и не пострадает.

И последняя деталь, о которой легко забыть: обычный запуск `docker compose up -d --build --wait` сразу применяет индекс `002`. Изолированный сценарий специально откладывает его создание до второй фазы — поэтому для воспроизведения эксперимента нужен именно `benchmarks.run`, а не ручной `up`.
