# ДЗ №2: воспроизведение нагрузки

Готовый результат: [отчёт с четырьмя графиками и EXPLAIN](../reports/search/REPORT.md).

## Полный запуск

Нужны Python 3.14, Docker и Compose **2.24.4+** (используется `!override`).
Нужны свободный порт 8081, несколько GiB диска и ресурсы для двух контейнеров
по 2 CPU / 2 GiB. Генератор работает на хосте. При 1000 клиентах желательно
иметь `ulimit -n` больше 2048. Прогон занимает несколько минут.

Из корня проекта:

```bash
# Если .env ещё нет, создать его и указать случайный JWT_SECRET длиной >= 32 байт.
cp .env.example .env
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-benchmark.txt
.venv/bin/python -m benchmarks.run
```

Если `.env` уже настроен, сохраняйте существующий файл. `run` сам скачивает
`people.v2.csv` в `data/`, собирает контейнеры и ожидает готовности API.

Сценарий запускает **отдельный Compose-проект `social-benchmark`**:

1. БД с собственной сетью и volume `social-benchmark_postgres_data`.
2. Только миграцию `001`, без индекса поиска.
3. Приложение на http://localhost:8081 с обычным пулом из 10 соединений.
4. Загрузку ровно 1 000 000 анкет через `COPY`; реальные ФИО, даты и города — из CSV.
5. `VACUUM ANALYZE`, проверку количества, сбор статистики и планов без индекса.
6. Три повтора на 1/10/100/1000 клиентов, окно запуска 15 с, прогрев 3 с.
7. Миграцию `002` с индексом и `ANALYZE`, сбор планов и те же замеры после индекса.
8. Проверку неизменности ответов, сохранение JSON, CSV, графиков PNG/SVG и отчёта.

Нагрузочные профили — в `queries.json`: частые, более редкие и отсутствующие пары
префиксов. Все пары равномерно чередуются по кругу. В прогоне нет регистрации,
логина и фоновой генерации данных. Синтетические аккаунты нельзя использовать
для входа; для обычного входа создайте пользователя через API.

После эксперимента БД остаётся с индексом и миллионом анкет. Исходный CSV исключён
из Git. Результаты и все сжатые журналы отдельных запросов включаются в Git.

## Повторный запуск

Чтобы повторить замеры на уже загруженной выделенной БД:

```bash
.venv/bin/python -m benchmarks.run --reuse-data
```

Загрузчик проверяет число записей и метаданные исходного файла. Без `--reuse-data`
он отказывается работать с непустой таблицей. Повторный прогон перезаписывает
результаты в `reports/search/`; перед ним сохраните предыдущие файлы, если нужно
сравнить разные эксперименты. Обычный Compose-проект приложения не меняется.

Параметры сценария:

```bash
.venv/bin/python -m benchmarks.run --duration 30 --warmup 5 --repetitions 3 --reuse-data
```

Для отдельной пробной БД можно задать `--rows 10000 --duration 3 --repetitions 1`.
Число строк нельзя менять при повторном использовании уже заполненной БД.
Отчёт для сдачи построен на полном миллионе, а не на пробном массиве.

## Что именно измеряется

`benchmarks/load.py` создаёт заданное число асинхронных клиентов с keep-alive.
Каждый ждёт полный ответ, затем запускает следующий запрос. В конце заданного окна
новые запросы прекращаются, все начатые дожидаются завершения. Timeout — 120 с.

- Latency: время от начала запроса до полного чтения тела, включая очередь и ошибки.
- Throughput: число ответов HTTP 200 с правильным телом / полное время, включая завершение очереди.
- Ошибки, статусы, реальная одновременность, CPU генератора и время завершения
  очереди сохранены отдельно. Ошибки не увеличивают успешный throughput.
- В таблицах и графиках — медианы показателей трёх прогонов, разброс — min–max.
- Это closed-loop тест фиксированной одновременности. Он не доказывает способность
  выдерживать фиксированный внешний поток RPS без очереди.

Проверка функциональной корректности выполняется перед нагрузкой. Во время нагрузки
проверяются HTTP-статус и SHA-256 всего тела каждого ответа. SQL `EXPLAIN` использует
тот же запрос и параметры, что HTTP-метод; планировщик к индексу не принуждается.

## Файлы и перестроение отчёта

```bash
.venv/bin/python -m benchmarks.report
```

Эта команда только читает сохранённые результаты и строит отчёт/графики,
не обращаясь к API или БД.

- `reports/search/REPORT.md` — итоговый отчёт.
- `results.json`, `summary.csv` — данные каждого прогона.
- `seed.json` — количество, уникальность, частоты имён, контрольная сумма источника.
- `raw/*.csv.gz` — запись каждого HTTP-запроса.
- `explain/*.txt`, `explain/*.json` — планы и параметры БД обеих фаз.
- `latency-before/after.*`, `throughput-before/after.*` — четыре графика в PNG/SVG.

## Отдельные операции и остановка

```bash
docker compose -p social-benchmark -f compose.yaml -f compose.benchmark.yaml exec -T app \
  python -m benchmarks.seed --rows 1000000

docker compose -p social-benchmark -f compose.yaml -f compose.benchmark.yaml exec -T app \
  python -m benchmarks.database --stage after

docker compose -p social-benchmark -f compose.yaml -f compose.benchmark.yaml down
```

`down` сохраняет массив. Чтобы удалить **только тестовую БД**, используйте ту же
команду с `down -v`; обычная БД приложения из другого Compose-проекта сохраняется.

Обычный запуск `docker compose up -d --build --wait` сразу применяет индекс `002`.
Изолированный сценарий специально откладывает его создание до второй фазы.
