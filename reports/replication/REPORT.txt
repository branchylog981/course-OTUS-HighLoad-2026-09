ОТЧЁТ ПО ДЗ №3: РЕПЛИКАЦИЯ POSTGRESQL
=====================================

Дата замеров: 10.11.2026 (UTC)
Стек: FastAPI + PostgreSQL 17, Docker, генератор на Python 3.14 / aiohttp


1. ЧТО СДЕЛАНО
--------------

К приложению из ДЗ №1-2 подключены две физические реплики (hot standby).
Чтение переведено с master на реплики, запись осталась на master.
Проверил три вещи: нагрузку на чтение до/после переноса, сам факт переноса
по pg_stat_statements и поведение при аварии master в двух режимах
(асинхронная репликация и кворумная запись).


2. КЛАСТЕР И МАРШРУТИЗАЦИЯ
--------------------------

- один master, два standby; реплики подняты через pg_basebackup -Xs -R
- wal_level=replica, hot_standby=on, wal_keep_size=512MB
- репликационные слоты не использовал: для стенда проще пересоздать
  отставшую реплику, чем рисковать забитым диском на master
- в приложении ReadRouter: /user/get/{id}, /user/me и /user/search
  ходят round-robin по двум репликам (2 пула по 5 соединений,
  транзакции READ ONLY); регистрация и логин — только на master
- если READ_HOSTS пуст, всё работает с master (режим ДЗ №1-2)


3. НАГРУЗКА НА ЧТЕНИЕ
---------------------

Данные: 1 000 000 анкет (тот же CSV, что в ДЗ №2). Смесь 50/50 из
GET /user/get/{id} и GET /user/search. Одновременность 1/10/100
клиентов, 3 повтора на точку, прогрев 3 с + окно 15 с, closed-loop,
keep-alive. Каждый ответ сверялся по SHA-256. Всего 82 543 ответа,
0 ошибок.

Суммарный RPS (медианы, master -> реплики):

  1 клиент  : 340.7 -> 313.9  (-7.9%)
  10 клиентов: 333.0 -> 286.1  (-14.1%)
  100 клиентов: 293.1 -> 255.9  (-12.7%)

Главный и честный вывод: перенос чтения throughput НЕ увеличил,
а немного снизил на всех точках. Master от SELECT при этом реально
освободился (см. п. 4). Причину не профилировал: на результат явно
влияют FastAPI, сериализация и сам генератор, всё на одном хосте.


4. ДОКАЗАТЕЛЬСТВО ПЕРЕНОСА
--------------------------

Дельты pg_stat_statements по узлам:

  фаза master:   master 21884+21887 вызовов, реплики — 0
  фаза replicas: master — 0, slave1 ~50%, slave2 ~50%

То есть чтение фактически ушло на реплики, счётчики сходятся
с числом HTTP-ответов по каждому методу.


5. АВАРИЯ MASTER И ПОТЕРИ
-------------------------

Генератор писал по одной строке за COMMIT и вёл внешний журнал
подтверждений (JSONL, flush/fsync). Master убивался SIGKILL через
3 с после первых подтверждений. Дальше — promotion самой свежей
реплики (по max pg_last_wal_receive_lsn) и подключение второй.

  async  : 512 попыток, 508 подтверждено, сохранено 0, ПОТЕРЯНО 508
  quorum : 432 попытки, 429 подтверждено, сохранено 429, потеряно 0

В async потеря показана при контролируемом разрыве репликационных
сетей перед аварией — так виден сам механизм потерь, а не «повезёт /
не повезёт». В quorum synchronous_standby_names = 'ANY 1 (slave1,
slave2)' + synchronous_commit=on: подтверждение только после flush
WAL минимум на одной реплике, т.е. запись живёт на 2 из 3 узлов.

Регистрация, чтение, поиск и логин после failover вернули HTTP 200
в обоих экспериментах. Переключение ручное, на это время запись
недоступна — нулевой downtime не заявляется.


6. ВЫВОДЫ
---------

- Кворум даёт гарантию: подтверждённая запись переживает гибель
  master. Цена — блокировка записи, если недоступны обе реплики,
  и чуть более медленный COMMIT.
- Async может терять подтверждённые транзакции; логин и запись
  после аварии корректнее вести только на новом primary.
- Перенос чтения на реплики — это про разгрузку master, а не про
  автоматический рост RPS: на однохостовом стенде выигрыша по HTTP
  не получилось.
- Автоматического failover в работе нет (Patroni не подключался),
  старый master после аварии нельзя возвращать без pg_rewind.
